# Getting the portal running

Written for someone who has not deployed an application before. It takes about
twenty minutes, most of it waiting for a build.

This uses **Render**, which was chosen for one specific reason: it builds and
runs this straight from the repository as a plain Node application, so there is
no container to build. It also hands you an HTTPS address on the spot, so you
need neither a domain nor an email account to get started — both can be added
later without redoing anything.

**Cost: about $7.25/month.** A Starter instance ($7) plus a 1 GB disk (~$0.25).
The free tier will not work: it has no persistent disk, which means the database
is deleted on every deploy.

---

## Before you start

You need a GitHub account with access to this repository, and a credit card for
Render. That is all.

The branch this lives on is `claude/espm-client-portal-l0re0p`. Either merge it
to your default branch first, or tell Render to deploy that branch in step 2.

---

## 1. Create the Render account

Go to [render.com](https://render.com), sign up **with GitHub** — that way it
can see your repositories without any extra setup — and authorise it for
`upadhyayameya/ControlApp`.

## 2. Deploy the blueprint

In the Render dashboard: **New → Blueprint**.

Pick the `ControlApp` repository. Render finds `portal/render.yaml` and shows
you what it is about to create: one web service called `hbs-portal` with a 1 GB
disk. If you have not merged the branch, change the branch to
`claude/espm-client-portal-l0re0p` on this screen.

Click **Apply**.

You do not need to fill in any of the environment variables it lists as
optional. `SESSION_SECRET` and `CREDENTIAL_KEY` are generated by Render itself,
so nobody — including you — ever handles them.

The first build takes five to ten minutes. Watch the log; the last line you
want is `[portal] listening on`.

Two lines in that log are warnings, and both are expected on a first deploy:

```
[portal] SMTP_HOST is not set — invitations ... are queued ... but not delivered.
[portal] WARNING: production with ESPM in fixture mode — no data will sync ...
```

Steps 5 and 6 turn each of those off.

## 3. Create your account

There is deliberately no default account and no sample data — a portal that
ships with a known login is a portal anyone can sign into.

In your service, open the **Shell** tab and run:

```bash
cd /opt/render/project/src/portal
npm run create-admin -- --email you@hbssolutions.com --name "Your Name"
```

(If that path does not exist, run `ls` and `pwd` — Render may already have put
you in the right place. You want the directory containing `package.json` and
the `server/` folder.)

It prints a password. **Copy it now** — it is not stored anywhere and cannot be
shown again. Change it after you sign in.

That creates an HBS staff account, which sees every organization. To create a
customer organization and its first admin together:

```bash
npm run create-admin -- --email ops@client.com --name "Their Name" \
  --org "Client Property Group"
```

## 4. Sign in

Your URL is at the top of the Render page, something like
`https://hbs-portal.onrender.com`. Open it and sign in with the account from
step 3.

The portal will be empty, with one button: **Connect Portfolio Manager**. That
is correct — there is no data yet.

---

## 5. Connect Portfolio Manager

Until this is done the portal runs on recorded sample responses and syncs
nothing real.

In Render: **Environment → Add Environment Variable**, three of them:

| Key | Value |
| --- | --- |
| `ESPM_USERNAME` | your Portfolio Manager web-services username |
| `ESPM_PASSWORD` | its password |
| `ESPM_ENVIRONMENT` | `test` while you are trying it, `live` when you are not |

Save. Render restarts the service. The `fixture mode` warning should be gone
from the log.

Then, in the portal, sign in as staff, pick an organization, and press **Pull
from Portfolio Manager**.

> Be prepared for this to need an hour of fiddling. The ENERGY STAR API was
> unreachable from the environment this was built in, so the live path is
> correct by construction and tested against recorded responses, but has never
> spoken to the real service. The likeliest problem is metric names: see
> *Known unknowns* in the README.

## 6. Turn on email

Without this, invitations are recorded but never sent — you invite someone and
they receive nothing. It works, in that an admin can copy the invitation link
out of the portal and send it by hand, but it is not what you want for
customers.

The quickest option is [Postmark](https://postmarkapp.com) or
[Resend](https://resend.com). Both are free at low volume and both will ask you
to verify a domain you own before they will send as your address.

Once you have credentials, add them in Render's **Environment** tab:

| Key | Value |
| --- | --- |
| `SMTP_HOST` | e.g. `smtp.postmarkapp.com` |
| `SMTP_PORT` | `587` |
| `SMTP_USER` | from your provider |
| `SMTP_PASSWORD` | from your provider |
| `MAIL_FROM` | `portal@hbssolutions.com` — must be an address the provider will send as |

Save. Within a minute the log shows `[portal] outbound email enabled`, and
anything queued while email was off is sent then, not lost.

## 7. Use your own domain

Optional, and best done once you are sure you are keeping this.

In Render: **Settings → Custom Domains**, add `portal.hbssolutions.com`, and
create the DNS record it shows you wherever your domain is managed. Render
issues the certificate.

Then add one environment variable, because invitation links need to point at
the new address:

| Key | Value |
| --- | --- |
| `PUBLIC_ORIGIN` | `https://portal.hbssolutions.com` |

Until you set this, links are built from Render's own address, which keeps
working — so this is a tidiness step, not an urgent one.

## Things worth knowing

**Back up the disk.** The entire application state is one file on the disk you
created in step 2. Render snapshots disks daily on paid plans; check that it is
on. To take one yourself, from the Shell tab:

```bash
sqlite3 /var/data/portal.db ".backup /var/data/backup.db"
```

Use that command rather than copying the file — copying a database while it is
being written produces a backup that will not open.

**Do not run two instances.** If you scale the service past one, the login rate
limiter and the scheduled jobs both misbehave: an attacker gets double the
login budget, and every scheduled job runs twice. Fixing that properly is
described under *One instance, for now* in the README. One instance is ample
for this workload.

**Deploys are safe.** Render sends the old instance a shutdown signal; it stops
accepting new requests, finishes what it is doing, and closes the database
cleanly. Nothing in flight is dropped and the disk is untouched.

**Watch the first bill.** Not because it is large, but because a disk that fills
up will take the service down, and 1 GB is a lot of this data but not infinite.

## If something goes wrong

**The build fails on `npm ci`.** Almost always `better-sqlite3` failing to find
a prebuilt binary. The log says so explicitly. Render's Node runtime is a
supported platform, so this is unlikely, but if it happens the fix is to pin
the Node version in `portal/package.json` rather than to fight the build.

**The site loads but every page is blank or 404.** The browser app was not
found. Check the log for `[portal] serving the web app from` — if that line is
missing, the web build did not produce output and `npm run build` failed
quietly.

**You cannot stay signed in.** The session cookie is marked `Secure`, so it
only works over HTTPS. On Render it always is; this bites people who try the
same setup on plain HTTP elsewhere.

**Locked out after too many attempts.** That is the rate limiter: five failed
passwords per account per fifteen minutes. Wait it out, or restart the service
from the dashboard — the counters are in memory and reset on restart.
